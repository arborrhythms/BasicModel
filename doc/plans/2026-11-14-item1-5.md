## The radix trie as a tensor, and the Pi in its place (Alec's question, 2026-11-18)

Alec, 2026-11-18:

> And one question about percept creation, which I think is using radix
> trie. If we create the tensor of all part codes in the hypercube, and
> that is what the PI selects, is there a wire-like method to activate
> those codes in the tensor in a neural-like part to whole flow graph,
> instead of using a radix tree? It feels like we might be able to make
> the radix trie fast if we give it a tensor implementation, possibly
> using a transition matrix to associate parts and wholes.

**What exists** (read at `6b55876710`).

- *The store.* `RadixLayer` (`bin/Layers.py`) holds a `RadixTrie` of
  Python nodes, a dictionary from bytes to a percept's id, a list from
  an id back to its bytes, and the codebook. A lookup is the
  dictionary, then the trie's longest match, then a fallback by bytes
  that counts hits and promotes a chunk into the trie.
- *Where it runs.* On the host, before the compiled part of a
  sentence: `PartSpace._embed_radix_word_major` ("Eager radix lookup
  ... Host tokenization/promotion remains outside the captured body").
  It gives index tensors, and the gather of codes is replayed from
  them.
- *A word's code is already a fixed function of its parts.*
  `WordIdentity.base_atoms`: the pairs of neighbouring bytes of the
  word with a mark at each end, and its lengths. `cat` is `#c`, `ca`,
  `at`, `t#` and the lengths 1, 2, 3. Each atom has a fixed set of
  bits (`bit_stream`), and the word's code is their union. Nothing in
  it is learned.

**Two forms that are wires.**

*A. The trie itself as a transition table.* A trie is a machine with
states: one table gives, for a state and a byte, the next state, and
one gives the percept that ends at a state. It is run for every start
place of the sentence at once, one gather for each step, as many steps
as the longest stored form; the longest match is the last ending seen.
Read as a matrix it is what he describes: a state vector times a
transition matrix for the byte. A promotion writes rows into the table
at the kept close, where promotions already wait. Results are equal by
construction.

*A small trial, run by Claude* (the real `RadixTrie` beside a table
built from the same forms): 31 forms, 82 states, longest 6 bytes; the
table agrees with `longest_match` at 173 of 173 start places of twelve
sentences. On 9,200 start places the host trie took 2.4 ms and the
table 1.3 ms. So the gain at this size is not time. It is that the
lookup is no longer a step on the host that the sentence's graph has
to stop for.

*B. No trie in recognition: the Pi.* Bytes give atoms by a table over
two neighbouring bytes, and the lengths; the code of a token is the
union of its atoms over its extent; and a row of the first Pi lights
when its atoms are there. That is a flow from parts to wholes in
matrices only, and it is what item 1.7 already has the Pi do (rule 8,
a basic percept is built by Pi; rule 32, a Pi finds the spellings).
What is still a table then: the way back from an id to its bytes,
which is a gather; and the admission of a new form, which becomes a
row that MTM nominates (sigma-pi §19.10) in place of an insert into a
trie. The one step that is a decision on the host today is the
repair of a collision of two codes (`WordIdentity`, "collision
mints").

**A larger trial, at a million forms** (Alec, 2026-11-18: "Can you make
a larger test of speed? We will have a 1M percept dictionary easily,
and a sentence at a time worth of percepts."). Run by Claude: 1,000,000
distinct word-like forms built from syllables (mean 8.6 bytes, longest
12), sentences of twenty words (187 bytes; one word in ten not in the
dictionary), the median of 200 sentences, on this machine while other
jobs ran. Nothing is compiled. The dictionary is synthetic.

*Finding the longest match at every start place of one sentence:*

| --- | ---: | ---: | ---: | ---: |
| Python trie (`RadixTrie.longest_match`) | 0.081 ms | the same | the same | the same |

| A, transition table, Metal | 1.16 ms | 0.086 | 0.022 | 0.0068 |

The Python dictionary, for the twenty words alone, takes 0.007 ms, and
the trie for the twenty words 0.03 ms. Both tensor forms agree with the
trie at 3,742 of 3,742 start places. A dense table of states by bytes
would need 3.1 million states by 256, so the table is kept as a sorted
list of edges read by `searchsorted`: 75 MB, built in 1.5 s. The Python
trie adds 0.23 GB and builds in 1.8 s. The hash is of 64 bits, with no
two of the million forms alike, and the stored bytes are compared
before a match is taken.

*Recognition from the atoms (form B), the twenty words of one
sentence:*

| Form | One sentence |
| --- | ---: |
| Posting lists, pair width 64 (today's) | 239 ms |

At width 64 each bit is in a third of the million rows; at 4,096, in
about 9,000. About a thousand of the million forms have the same atoms

the case the collision mints exist for. Syllable words repeat pairs

*What it says.*

- Taken alone and on the CPU, the trie is not slow. One sentence costs it under a tenth of a
  millisecond at a million forms, and its size hardly matters. As a
  tensor it is two to fourteen times slower for one sentence, level at
  about sixteen sentences in one call, and faster beyond.
- So A is worth having for what it removes, a step on the host inside
  a sentence, and for many sentences at once; not for speed at one
  sentence.
- B is where the time is. Matching a sentence's words against a
  million rows costs hundreds to thousands of times what the lookup
  costs, unless the rows are narrowed first. One way that keeps both:
  the lookup names the candidate rows, and the Pi reads only those.

**Is it invertible as the trie is** (Alec, 2026-11-18: "is it
invertible in the same way an orthographic trie is?"). Yes, exactly,
and by the means the store uses today, which is not the trie.

- *What exists.* The way back from a percept's id to its bytes is a
  list, `RadixLayer.inverse_table` ("Exact, no learning"). The trie's
  nodes hold no way up to their parent, and the source uses the trie
  only to insert, to load and to match. Which parts a promoted form is
  made of is kept apart from it as well (`part_groups`).
- *In the tensor form* that list is a table of bytes, one row for each
  id, and the way back is a gather. In the prefix hash it is the same
  table that makes a match exact.
- *Checked by Claude:* 300 sentences, one word in five unknown, tiled
  by the longest match with single bytes where nothing matches. The
  tensor lookup gives the same percept ids as the real trie on 300 of
  300, and the text comes back exactly from both.
- *What only the structure of a trie gives:* a form's prefixes are its
  ancestors, and the forms that share a prefix are one subtree. The
  source does not use it. The transition table of form A keeps it (a
  parent and a byte for each state, read upward); the prefix hash does
  not, and a prefix is then a question put to the bytes.
- *The atoms of form B are not invertible alone:* about a thousand of
  a million forms share their atoms with another. Their way back is
  the same table of bytes.

**Parts in an area give the whole: the tree in the codes** (Alec,
2026-11-18).

> If "ab" and "bc" are present within a three-character area, then
> we know that "abc" is present in that area. I see that as the basis
> for computation of a mereological tree, which is what we want for
> the codes, not just a hash. Is that correct?

Correct, with one condition, measured by Claude on the system's word
list (234,454 words).

- *The inference holds when the order of the two parts is known.*
  With the left part and the right part one place on, a pair of parts
  has exactly one whole: of 2,192,462 such joins in the word list, no
  pair of parts has two.
- *Presence in the area alone leaves two readings where the outer
  letters are the same:* `ab` and `ba` in three letters are `aba` or
  `bab`. That is 88,191 of 1,779,760 three-letter areas, 5 in 100.
  His own example is not one of them.
- *Today's codes drop that order.* A word's atoms are its pairs as a
  set, with a mark at each end, and its length. In the word list 80
  words in 40 groups have all their atoms in common with another word
  (`acara` and `araca`, `anasa` and `asana`). With each pair kept at
  its place there are none. These are the cases the collision mints
  repair one at a time.
- *It is what the codes should be, and are in kind.* A whole's code
  holds its parts' codes, so that parthood is read from the codes
  themselves. The prefix hash recommended above is only the address by
  which a form's row is found; it is not the form's code and replaces
  no code.
- *As a computation on tensors:* one table from a left part and a
  right part one place on to their whole, probed for every pair of
  neighbours in the sentence at once, level after level. Read the
  other way it gives a whole's two parts, so the tree is invertible
  by its structure. This is the "transition matrix to associate parts
  and wholes" he asked about, and what a promotion records today as
  `part_groups`.

*Then* (Alec, 2026-11-18): "So "if these parts are present here,
then this whole is present here", and we need not worry about order

- *The order of composing is free.* The rule is a conjunction, and a

## Where a sentence's time goes, and five steps for it (added 2026-11-19)

Alec, 2026-11-19, on the list below: "Please add this to the 1.5 work
(assuming that is the future compiler optimization item), most seem
like things you can do in parallel with 1.6."

**The last profile** (2026-11-17; one worked math-chain document of 12
sentences, eager, on the host, `cProfile`; the zero-data-movement
document has the census). It is older than item 1.8's landing and item
1.7, so it is taken again on the source that item 1.7 leaves before
any text is written from it.

| Share of one sentence's time | |
| --- | ---: |
| scoring the candidate paths | 45% |
| the read | 26% |
| the sentence's optimizer step | 12% |
| the kept close | 9% |

One sentence made 10.0 million Python calls and 1.1 million calls into
torch, and read a tensor back to the host 24,547 times (22,030 of them
`.tolist()`). About three quarters of the time was host code outside
the read. It was not transfers from an accelerator: the run was on the
host. On an accelerator each of those reads waits for the device, so
the same pattern costs more there.

**Five steps, largest first.**

1. *Score the candidate paths as one batch, or score fewer.* They are
   scored one at a time in Python. Stack them into one call; share the
   work of a common beginning; prune sooner.
2. *Look up a sentence's percepts once* (the percept pass, already in
   this item's second part): the profile had 1,924 calls of
   `Codebook.lookup_rows` and 63 reads of a whole table in a sentence.
3. *No read of a tensor on the host inside a sentence.* A decision
   stays on the device as a mask and is read once at the sentence's
   end. Four fifths of the `.tolist()` calls came from one walk of the
   pinned tree (step A of the first part removes that walk).
4. *No hook on every saved tensor:* it was about two fifths of all
   calls into torch (`SentenceCompose.saved_sentence_values`).
5. *The recurrence over the words is the floor.* Capture removes the
   dispatch and not the chain (1.8 times at 64 words, measured on
   Metal on 2026-07-08). What moves it: a larger batch (1.7 times at
   256, measured) and bf16 on an H100 (about 2 times).

**What can run beside item 1.6** (*Claude's reading of "most"*). Steps
1, 3 and 4 touch the walk, the close and the hooks, and nothing of
item 1.6's number modality or corpus, so they can be built while item
1.6 is built. Step 2 waits for item 1.7's bank of one sentence, which
it replaces the lookups of. Step 5 is configuration.

**Adding a percept** (measured 2026-11-19, on item 1.7's source after
its round 3d: the 19,821 words admitted under a profiler, 82 s). Alec:
"is the problem constructing a mereologically correct code, or the time
of making parthood links across the tensor?" Neither the making of the
code nor the writing of it: 41% of the time tests the new code against
every stored code for one lying inside another
(`WordIdentity._accidents_of_many`), and 27% finds the links, the
stored forms it holds and that hold it (`WordIdentity._link`), by
looking through the stored forms. Choosing the coordinates is 5% and
writing the changed codes 4%. Both searches grow with the store. Here:
the links from an index of runs, and the test as one product on the
device.

*Measured the same day, on Alec's proposal* ("Since they are all
matrices, why can't we just run the comparison algorithm itself on the
part powerset of the code being inserted, and take the intersection of
those results?"; sigma-pi plan §19.90). A stored code holds the new
code exactly when it holds each of its parts' codes, so the

## The explore paths as rows of the batch (Alec, 2026-11-19)

Alec, 2026-11-19, thinking about the chooser's two paths: "I'm thinking
about ways to get more than a pair of explorations in per sentence."
Two ways he raised, a soft superposition of the unary operators at
every place and all the branching operators at a place of departure,
he set aside the same hour ("I'm seeing a lot of entanglements of
operator choice in the code (particularly the part of speech
influence). so the effects are too wide reaching"). What he asked
next: "I think we have a variable governing the number of different
explore runs we do per sentence, and perhaps that variable can be
tuned to learn over multiple iterations in a way that is much more
efficient than batches? Do you see good opportunity to stage multiple
explore runs at once (like, do we need only multiple parallel parse
trees?)" And then: "yes, lets explore implementing the explore paths
as separate batches which share data structures and sequencing in
1.5".

**What exists** (read at `d156e892cd`; nothing measured).

- The variable is `explorePaths` (`data/model.xml`, 1). A sentence
  runs one greedy path and that many explore paths, each departing
  once from the greedy one (`doc/GradientFlow.md`, "Whole-path
  credit").
- The paths run one after another, in three loops over the variable:
  the attention read (`Examination.py`), the compose walk
  (`Models.py`, `compose(cache, first)` then `score`), and the output
  walk (`WholePaths.py`).
- An explore path reuses the sentence's reading (the `cache`) and
  joins the greedy walk at its departure with no replay of the prefix
  (`SentenceFork`).
- Between paths the state is saved and put back
  (`WalkTrials.ThoughtTrialState`): STM's live chunks and thought
  contents, the slots of thought, the conceptual field with its where
  and when, the concept activations, both clocks, the record of
  memory activity, the strata of thought. The path being run is also
  published on the model as single records (`_sentence_departure`,
  `_sentence_trial`, `_sentence_cost_registry`,
  `_compose_forced_slots`, `_attention_words`, and the "last" records
  of the output walk).

So a path is the parse tree and everything a walk writes as it goes.
It is more than parallel parse trees.

**What the variable buys.** The greedy path is the baseline of every
explore path, so K explore paths cost about 1 + K walks and give K
comparisons: a half for each walk at one, three quarters at three,
nine tenths at nine; less than a walk each where the departure is
late. They buy credit for the chooser and for the operators the
greedy path did not select. Reconstruction and expectation see the
same sentence K times (the 2/(1+K) scale), which teaches them less
than K sentences would. So it is better than a larger batch where
the chooser is what holds learning back, and the explore-win rate by
level says where that is. A short sentence has few distinct
departures.

**The design to explore: the paths are rows of the batch.** A batch
already keeps a tree, an STM and a field for each stream, and the
choice of the kept row for each sentence exists
(`SentenceCompose.select_rows`, `ThoughtTrialState.keep`). A sentence
is K + 1 rows over one shared reading; each row departs at its own
draw; the steps of the walk run once for all rows, in one sequence.
Nothing is saved and put back.

What the copies of one sentence must share, or do once:

| Shared thing | Why |
| --- | --- |
| The reading: the percept pass, the first Pi, the bank of the sentence | It is the same for every path; it is the `cache` now |
| The sequencing: the loop over words and rounds | One loop for all rows; a row that has departed differs only in its choices |
| MTM's count of readings | A reading is one sentence in one stream (`Spaces.nominates`); three copies of a word must not be three readings |
| Writes to LTM, and whatever a sentence admits | The kept path's only |
| The clock | One tick for all copies of a sentence (sigma-pi plan, rule 64: one integer clock) |

What each path must have of its own: every record the list above
names as saved between paths, and every single record of "the path
being run" on the model, which takes a path axis or becomes a row's.

**Order of work** (*Claude's*).

1. A census, read-only: every thing a walk writes, by owner, and for
   each whether it is already held by stream. It starts from
   `ThoughtTrialState`'s list and from the model's single records.
2. A trial of the attention read alone, which is the smallest of the
   three loops and already selects rows (`select_rows`): K readings
   as rows, equal results with the loop at the same draws.
3. The compose walk, then the output walk, each with equal results
   against the serial loop at the same draws before the loop is
   removed. No second path is left beside the new one.
4. The measure: seconds a sentence at one, three and seven explore
   paths, serial and as rows; and on the lesson, what the chooser
   learns in equal time at each.

This is step 1 of the five above ("Score the candidate paths as one
batch") made whole: not the scoring alone, the paths. It touches the
walk and the close, and nothing of item 1.6, so it can be built
beside it.

- Two things to read in that measure, since autocast narrows what it chooses and not what we choose: that a count held as a float stays exact (exact only to 2,048 in half precision), and that the Pi's fold does not reach nothing sooner (the least normal half-precision value is about 6e-5).

## Codex's four moves for the chooser (Alec, 2026-11-21)

Alec: "Codex has suggested the following moves chooser, I think all of them look like they should go in 1.5". Codex's text, whole:

1. Preserve alternatives whose next legal move can differ. _distinct_departures can group two actions when they produce the same numerical stack, depth, reference choices, and order change. But the next round also consults the previous unary operation to mask its inverse. Two actions can therefore look equivalent to the exploration filter and still lead to different legal continuations. Once the filter discards one, the chooser cannot learn which continuation works better. I'd include the resulting unary history in the equivalence check and retain separate alternatives wherever their recorded operations can change reconstruction or the answer. Their identical numerical results can still share storage. (Departure grouping; Inverse mask)

2. Keep soft probabilities on both paths and carry each interpretation separately. The live chooser assigns a distribution over legal actions, executes one action per path, and learns from the difference in completed reconstruction-plus-answer cost. That distinction matters for language. intersection and union can both reconstruct the same two words, yet give different answers about an object possessing only one property. Averaging their stack vectors before the answer would obscure the distinction the chooser needs to learn. I'd share the prefix, then let each suffix compute its own logits from its own operands, role evidence, and legal moves. For early language learning, I'd use the existing bracket lessons to credit the sum of probabilities of acceptable actions, then use meaning-sensitive examples to distinguish them. That gives the model a useful signal before it knows enough vocabulary to answer reliably. (Whole-path credit; Grammar lesson probabilities)

3. Make the same chooser scores cheaper to compute. MLPTransformChooser._score expands the slot, tool, and position features across candidates, concatenates them with each candidate result, then applies a linear layer. That layer can be written as Wslot.slot + Wcandidate.candidate + Wtool.tool + Wpos.position + bias, followed by the existing GELU. The slot projection is then paid once per location and the tool projection once per tool. This preserves the learned weights, signed operand-order features, and scoring function up to floating-point rounding. I'd also give greedy evaluation a scoring path that skips constructing equivalent-departure groups whenever no caller needs them. These are concrete opportunities to reduce temporary tensors on this 24 GB M2. The pilot XML's batch size of 28 was documented for a 36 GB host. (Chooser implementation; Departure construction; Pilot configuration)

4. In Pi-Not-Sigma, share the open read and keep the request path-specific. I'd compute the sentence's active percepts and local Pi derivatives once. Each path can then pull its own conceptual request back through those values and intersect it with its own .where salience. For that pullback, I'd use each Sigma's pre-tanh sum. In the recorded prototype, the ordinary gradient recovered the requested words in 230 of 304 cases. Passing Sigma before saturation recovered 304 of 304. The open question is how it behaves with partially present evidence, precisely where two plausible readings should receive different weights. (Salience experiment; What and where intersection)

For the eventual decision, I'd use examples and wall-clock time to reach a fixed accuracy on held-out sentences whose meaning changes with the parse. That captures both senses of "learn quickly." The existing eager CPU profile attributed 45% of time to scoring completed paths and 26% to compose overall. Chooser latency matters, but the larger payoff may come from spending each explored path on an interpretation capable of teaching the model something different.

*Claude's notes, not checked in the source.* Moves 1 to 3 are this item's; in move 2, crediting the sum of the probabilities of the acceptable actions changes what a bracket lesson teaches and is put to Alec before it is built. Move 4 is overtaken in part by item 1.7 (sigma-pi plan, §19.121): the request is carried down by the layers' ways back and not by the derivatives, and a look takes no `.where` of its own, since the `.where` is muxed into the concept; what stays for this item is that the sentence's field is read once and each explored path carries its own request down. Codex's closing measure (examples and wall-clock time to a fixed accuracy on held-out sentences whose meaning changes with the parse) is the gate for these moves.

## Codex on the memory structures, with Alec's comments (2026-11-22)

### A form is its two parts one letter shorter (decided 2026-11-25)

### A form's code: a vector in perceptual space, sorted by both towers (Alec, 2026-11-25)

Asked whether the code is a sparse vector as wide as the table: "No,
the code is a vector in perceptual space." Asked its width: "64 +64",
and of the two readings, "Parts plus wholes is correct, it is sorted by
both towers". Of the increment: "nothing in mind".

So a form's code is 128 wide, in two halves of 64.

- *The parts half* rises from parts to wholes: a whole's is the
  coordinate-by-coordinate maximum of its two parts', plus an
  increment. A whole is at least its part in every coordinate.
- *The wholes half* rises from wholes to parts: a part's is the maximum
  over the wholes that hold it, plus an increment, raised at the reset
  when a whole is admitted. A part is at least its whole in every
  coordinate.
- Forms that share parts, or share wholes, inherit the same maxima and
  lie near each other.

*Claude's, for the build, his to change:* the increment is a fixed step
on a few coordinates of the half, chosen by the form's row number, so
each form rises a little in a direction of its own; a single byte's

whole has a wholes half of nothing.

### The code as a density order embedding (Alec, 2026-11-25)

particular attention to the last link." The last link is Athiwaratkun and Wilson,

- Each node is a Gaussian with diagonal covariance: a mean and a
  variance for each coordinate. A specific node is narrow, a general
  one broad; f is below g when f lies inside g.
- The penalty of a pair (specific f, general g) is
  `d(f, g) = max(0, KL(f || g) - gamma)`, with
  `2 KL(f||g) = log(det S_g / det S_f) - d + tr(S_g^-1 S_f) + (mu_f - mu_g)^T S_g^-1 (mu_f - mu_g)`.
- The loss over true pairs (u, v) and false pairs (u', v') is
  `d(u, v) + max(0, m - d(u', v'))`. False pairs: a random node put in
  place of one end; the pair reversed; and two nodes under a common
  ancestor of which neither holds the other. Three false to one true
  did best.
- Variances all start at one small value and are learned as their
  logarithms; means start at unit length; Adam. Their best: m 2000,

  82,115 nodes, trained on the transitive closure.

### Handoff, added: traversing all parts without counting twice (Alec, 2026-11-25)

Alec: "if we want an algorithm that traverses all parts, and we select
the maximal left and right parts, there is some risk of overcounting.
So we must traverse the left and all parts that contain the left, and
the right and all parts that contain the right. That will leave a set
in the middle which has not been traversed, which corresponds to
traversing either the left-then-right, or the right-then-left."
Correct. Every part of a form of length n is in exactly one of three
groups: those touching its left end (its prefixes, by left links, n-1
of them), those touching its right end and not its left (its suffixes,
by right links, n-1), and those touching neither, which are the middle
(right of the left link = left of the right link, one row) and the
middle's parts. So: prefixes, suffixes, then the same on the middle,
entered once. Counts: 2(n-1) + 1 + the same for n-2, in all
n(n+1)/2 - 1. This is exact by position; two positions may still hold
one row (`aa` in `aaaa`; `ab` at both ends of `abab`), so an algorithm
that must touch each distinct form once still marks the rows it has
visited.
